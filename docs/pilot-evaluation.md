## 1. 결과를 읽는 원칙

- **파일럿 결과는 `docs/content-backlog.md`의 stage가 `published`인 12편만 기준으로 읽는다.** 이 12편은 아래 3절 표 A에 그대로 옮겨 두었다. 백로그의 `published` 행과 이 표가 다르면 백로그가 맞다.

- 시험 기간 중 선정·제외 기준은 바꾸지 않는다(`blog-c-site-structure.md` 4절). 점검 중에 바꾸고 싶은 점이 생기면 기록만 하고 평가 때 다룬다.
- 점검은 **관측과 기록**이다. 숫자가 낮다고 글을 고치거나 다시 발행하지 않는다. 사실이 바뀐 것을 발견했을 때만 해당 글의 재확인 절차를 따로 시작한다.

## 4. 점검 전에 해 둘 일 (사용자 쪽)

Claude는 사용자의 Search Console 계정에 접근하지 않으며, 로그인·비밀번호·계정 연결은 사용자가 직접 한다. 숫자는 **사용자가 화면을 보고 알려 주거나, 내보내기(CSV) 파일을 저장소 밖 폴더나 대화에 올려 주면** Claude가 표에 옮겨 적는다.

1. **Search Console 속성 만들기.** 선택지는 두 가지다. URL 접두사 속성(`https://statesideexplained.com/`)은 확인 방법이 여러 가지라 쉽고, 도메인 속성은 DNS 레코드를 넣어야 하며 `www`·`http`까지 한 속성으로 모은다. `www` 주소가 아직 열리지 않으므로 지금은 URL 접두사 속성이 단순하다는 것이 Claude의 판단이다. 결정은 사용자가 한다.
2. **소유 확인.** 확인 방법은 Search Console 화면이 안내하는 것을 따른다. 어떤 방법을 썼는지 표 E에 적는다.
3. **사이트맵 제출.** Sitemaps 화면에 `sitemap_index.xml`을 넣는다(전체 주소는 표 E). 제출 날짜를 표 E에 적는다.
4. **색인 요청을 쓸지 정하기.** URL 검사의 "Request indexing"을 쓰면 발견 속도가 달라져 "자연 발견" 관측이 흐려진다. 쓴다면 **어느 글에 언제 눌렀는지** 표 B·C의 메모에 적는다. 쓰지 않는 쪽이 파일럿 관측에는 깨끗하다(Claude의 판단).
5. 1주 점검 전에 속성이 없으면 **수동 검색 항목만으로** 표 B를 채우고, Search Console 열은 `—`로 둔다. 소유 확인 직후에는 데이터가 비어 있는 것이 정상이므로 그 사실도 메모한다.

## 8. 점검 기록을 남기는 방법

1. 점검한 날, Claude가 표 B(또는 C)·D·E의 해당 열을 채운다. 값은 사용자가 알려 준 것, 내보내기 파일에서 읽은 것, Claude가 공개 페이지에서 확인한 것으로만 채우고 출처 라벨을 붙인다.
2. `docs/decision-log.md`에 점검 항목을 하나 남긴다: 점검일, 본 것, **못 본 것**(예: Search Console 속성이 없어 `—`), 눈에 띄는 변화.
3. 이 문서와 결정 로그를 로컬 커밋한다. 사용자가 push한다.
4. 점검 중에 글을 고쳐야 할 이유가 발견되면(예: 공식 페이지 변경) **점검 기록과 분리해** 해당 글의 재확인·수정·Gate 2·사용자 승인 순서를 따른다.
5. 표의 열을 바꾸고 싶으면 이 문서를 고치고 결정 로그에 이유를 남긴다. 이미 채운 값은 지우지 않는다.
